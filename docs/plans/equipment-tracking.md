## Decision — the field entry point is a Telegram Mini App

**Resolved (v3): the Mini App branch is primary.** The v2 Phase 0 device gate is removed — not because the question stopped mattering, but because the decision is made and the test could not have answered it anyway.

The corrected assumption, recorded so it doesn't resurface: v1/v2 argued "every user already has an account _and a live session_", and the second half is false for a meaningful slice of this team. Some members rarely open the web app and will live in Telegram only. For them, two things compound on iOS:

- Safari's ITP deletes script-writable storage — including first-party `localStorage`, where the Supabase session lives ([lib/supabase.ts](../../lib/supabase.ts) default) — after ~7 days without interacting with the site. A monthly-at-best user arrives at _every_ scan with no session. (Home-screen-installed PWAs are exempt from this cap, but a camera scan opens Safari, not the installed app — so the exemption never applies to the scan path.)
- A person who never uses the web app doesn't remember their password. The field flow becomes: scan → Safari → login screen → password recovery → abandoned, while the crew waits.

The Mini App has no session to lose: Telegram hands the page a fresh `initData` on every open, so identity is re-established automatically each time.

**Why the v2 device test is dropped rather than run:** it would have produced a **false pass**. Test phones belong to people who use the app — their Safari sessions are days old, not weeks. The failure mode only manifests after 7+ days of non-use, in the field, on exactly the phones nobody tested. A gate that can't detect the failure it gates on is theater; the decision is made up front instead.

**The cost, stated loudly:** Telegram linking changes from _optional_ to **mandatory for every field user** — the Mini App cannot map a Telegram identity to a profile without a `telegram_links` row. That creates a bootstrap problem (the current linking flow starts in the web app's Settings — exactly where this population doesn't go), resolved in §5/§6 via admin-initiated codes and folded into the stickering day in the rollout checklist.

What does **not** change with this branch: data model, RLS, notification wiring, overdue cron, the web registry/manager view, and the physical rollout — the Mini App is an _entry point_ into the same SPA route, not a second application.

## 2. Recommended approach

1. **Two new tables** (`equipment_items`, `equipment_checkouts`) plus an append-only `equipment_verifications` table; current holder is _derived_ (the open checkout row), never stored redundantly.
2. **QR encodes `https://t.me/managment_system_bot?startapp=<ASSET_CODE>`** with the human-readable code printed under it (**changed in v6**: the bot uses a _Main_ Mini App, set in BotFather → Bot Settings, which takes `?startapp=` directly on the bot username — no `/<app_short_name>` segment and no `/newapp` step. Confirmed against core.telegram.org/bots/webapps; a named Direct-Link app would need the extra path segment). The shorter URL means fewer QR modules, which is exactly what a small sticker on field gear wants. Native cameras open Telegram → Mini App with the code in `start_param` (also exposed as the `tgWebAppStartParam` GET param). **Verified against Telegram's `startapp` constraints**: allowed characters `A-Z a-z 0-9 _ -`, max 512 — the plan's `^[A-Z]{2,4}-\d{3}$` codes (uppercase, digits, one hyphen) pass unchanged.
3. **Auth**: a new edge function validates `initData` server-side and exchanges it for a **real Supabase session** for the resolved profile, so every subsequent read/write flows through the existing `lib/database.ts` + RLS path unchanged (§5).
4. **Linking**: reuse `telegram_links` as the identity bridge; add an admin-initiated code flow to bootstrap the users who never open the web app (§5, §6).
5. **Bulk**: Telegram's native `showScanQrPopup` scanner (Bot API 6.4+) with continuous scanning replaces the v2 localStorage cart entirely; selection is plain component state (§6).
6. **Notifications & overdue**: unchanged from v2 — three new types through `notify()`/`notifyMany()`, overdue push via a cron-driven Vercel function; the overdue _badge_ needs no cron (computed at render).
7. **Registry/manager view**: unchanged — a normal web route for desktop use.

## 5. Backend surface

Core reads/writes: new functions in `lib/database.ts` under RLS, called from a `dataStore` slice with the standard optimistic pattern — same as v2, with three changes:

- `checkoutEquipment(items[], {expectedReturnAt, purpose, taskId?, holderId?})` — N inserts sharing a `checkout_group_id` (holder_name and group-holder consistency enforced by triggers, §4)
- `checkinEquipment(checkoutId, {note?, needsRepair?})` — writes only the checkout row; no item write
- **`transferEquipment(checkoutId, newHolderId)` → `supabase.rpc('transfer_equipment', …)`**, a `SECURITY DEFINER` Postgres function doing check-in + check-out **in one transaction**. v2's "two sequential writes, lost race is safe" was wrong: after a lost race the gear is physically in someone's hands while the registry says shelf — worse than either endpoint. RPC precedent is established (§1), definition ships in the Phase 1 migration.
- `markItemVerified(itemId)` — INSERT into `equipment_verifications`; **any full-scope user (v5, widened from v4's admin-only)** — the shelf walk happens in the Mini App with the scanner (§6.7), and whoever walks the shelf (realistically a gear manager on the `user` role) must not need the admin role for it. Verifications are append-only evidence with `verified_by` recorded — worst-case abuse is noise rows; the _interpretation_ (discrepancy list, check-in-as-found) stays admin-only in the registry.
- Offboarding guard (decision 4, v5): the delete-member flow first lists the person's open checkouts and blocks deletion until each is closed — by a normal check-in, an admin **force-close with a mandatory note** (mechanically just a third-party check-in, which decision 2 already allows), or by marking the item `lost` (new status, §4) when gear genuinely walked off. The guard is **app-level in the delete-member flow, by design**: profile deletion already `SET NULL`s the ledger and `holder_name` survives (§4), so integrity never depended on the guard — it exists so offboarding _notices_ outstanding gear, and an admin routing around it in SQL loses nothing but the reminder.

### `equipment-auth` — new Supabase Edge Function (Mini App auth)

Validates Telegram `initData` per the current Bot API recipe and exchanges it for a Supabase session. **The design is approved as-is (v4, owner decision)** — the trade-off is stated honestly in §8; no 2FA, no session caps, no rate limiting beyond Supabase defaults. Mechanism:

1. Accept the **raw `initData` string** only (never `initDataUnsafe` — client-side, forgeable).
2. `secret_key = HMAC_SHA256(key: "WebAppData", data: bot_token)`; expected hash = `hex(HMAC_SHA256(key: secret_key, data: data_check_string))`; data-check-string = every received field **except `hash`** (the `signature` field stays in — it is excluded only in the third-party Ed25519 validation path), sorted alphabetically, `key=value` joined by `\n`. Compare constant-time against the `hash` param.
3. Reject stale `auth_date` (freshness window ~5-15 min).
4. Resolve `user.id` → `telegram_links.chat_id` → `profile_id` (in private chats chat id equals the Telegram user id — which is what the webhook stored). Unlinked → structured "not linked" response (§6.5). Offboarding needs no special handling here: `telegram_links.profile_id` is `ON DELETE CASCADE` ([20260221100000…:4](../../supabase/migrations/20260221100000_create_telegram_links.sql)), so a deleted profile takes its link row with it and resolution simply fails.
5. **Profile-state check before minting** (new in v4): the same lookup selects `access_scope` and refuses the exchange unless it is `'full'`, returning a distinct response the UI can render. **Deliberately NOT gated on `profiles.status`** — the review assumed a deactivated-account state exists; the code says otherwise: `status` is `'active' | 'sick' | 'vacation' | 'remote'` ([20260218000000_initial_schema.sql:18](../../supabase/migrations/20260218000000_initial_schema.sql), [types.ts:109](../../types.ts), unchanged by any later migration) — a _presence_ field, not an account state. Blocking non-`active` would lock out exactly the people taking gear on a business trip. The schema has no deactivated state at all; offboarding is hard-delete, already covered by the cascade in step 4. Flagged as an instruction-vs-code conflict; the code wins.
6. **Session exchange**: `auth.admin.generateLink({type: 'magiclink', email})` for the profile's auth user (every profile has one, created via `inviteUserByEmail` — §1), return the `token_hash`; the Mini App calls `supabase.auth.verifyOtp({type: 'magiclink', token_hash})` and holds a normal session.

**Exchange timing, stated so nobody wires it wrong** (v4): `initData` is generated at webview open and does **not** refresh while the app stays open — a crew scanning 8 items over 20 minutes holds stale `initData` the whole time, by design. Therefore: the exchange runs **once, at open**; the minted session then lives on the normal Supabase token-refresh cycle; re-exchange happens only at the _next webview open_, with fresh `initData` — **never as a retry on a 401 mid-session**. Wiring re-exchange to the first auth failure would ship something that breaks in the field 15 minutes into a shoot.

Why session exchange over the stateless `gear-api` alternative: the minted session is the user's own session, so every equipment query runs through the existing `lib/database.ts` + RLS path with **zero forked code paths and zero authorization logic re-implemented in Deno**. If Telegram's webview storage drops the session, the next open re-exchanges silently. **The generateLink→verifyOtp pattern is documented but unverified in this project — the technical prototype still comes first in Phase 2**; that is a "does it work here" question, not a security one (settled). The prototype includes the Auth `/verify` rate-limit check (§9, §10).

### Admin-initiated linking (bootstrap, new)

Current `telegram_links` RLS is strictly self-scoped (all four policies `profile_id = current_profile_id()`, verified `20260811…:2241-2250`), so an admin cannot generate a code for someone else today. Add a `SECURITY DEFINER` function `admin_generate_telegram_link_code(p_profile_id)` (guarded by `is_admin() AND is_full_access()`, mirroring `set_member_access_scope`) + a `database.ts` wrapper + a "Generate Telegram code" button in the members admin UI. It also serves **re-linking** (someone changed Telegram accounts): the function clears the stale `chat_id` before issuing the new code, sidestepping the webhook's "already linked" guard (`telegram-webhook/index.ts:71-78`). ## 8. Security model

| Action                                                                                                                                 | user                     | editor | admin | related_only                    |
| -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ | ------ | ----- | ------------------------------- |
| View registry, holders, history                                                                                                        | ✔                        | ✔      | ✔     | ✖ (resolved: out of scope, §11) |
| Check out for self (incl. multi-scan)                                                                                                  | ✔                        | ✔      | ✔     | ✖                               |
| Check in / transfer / flag needs-repair                                                                                                | ✔ (resolved: decision 2) | ✔      | ✔     | ✖                               |
| Audit scan — verify items on the shelf (v5)                                                                                            | ✔                        | ✔      | ✔     | ✖                               |
| Check out on behalf; edit/delete history rows; force-close / mark `lost`                                                               | ✖                        | ✖      | ✔     | ✖                               |
| Item CRUD, retire, status flips, QR printing + mark-as-printed, audit _analysis_ (discrepancies, check-in-as-found), link-code issuing | ✖                        | ✖      | ✔     | ✖                               |

Enforced in **RLS** (UI gating is mirror only):

- All three tables: `SELECT TO authenticated USING (is_full_access())` (helper verified, `20260811…:273`).
- `equipment_items`: `INSERT/UPDATE/DELETE` → `is_admin()`. **Full stop — no non-admin writes remain** (needs-repair lives on the checkout, verification in its own table), which deletes v2's unresolved column-granularity risk. No triggers-for-authz, no column grants.
- `equipment_checkouts`: `INSERT` → `is_full_access() AND (holder_id = current_profile_id() OR is_admin())`; `UPDATE` → `is_full_access() AND (is_admin() OR checked_in_at IS NULL)` (closed history immutable to non-admins); `DELETE` → `is_admin()`. Integrity triggers (`holder_name`, group-holder, asset-code immutability) are `SECURITY DEFINER`-independent data rules, not authz.
- `equipment_verifications`: `INSERT` → `is_full_access()` (**widened in v5** from `is_admin()` — the pick, explicitly: the person walking the shelf may be a gear manager on the `user` role, and the admin-only policy would have locked them out of the whole exercise; verifications are append-only evidence with `verified_by` recorded, so the worst-case abuse is noise rows, while the _interpretation_ stays admin-side). No UPDATE/DELETE policies at all — append-only by construction.
- `transfer_equipment` RPC: SECURITY DEFINER; internally re-checks `is_full_access()` — per decision 2 (any full-scope user may check in or take over) that is the whole guard; mirrors how `save_task_with_relations`-style functions carry their own checks.
- **The session exchange changes what a linked Telegram account _is_** (corrected in v4 — v3's "grants nothing new" claim was wrong and is retracted). Linking stops being a notification-delivery channel and becomes an **authentication factor**: anyone who controls a linked Telegram account can mint a full session as that user — the whole tool, not just equipment, read-write. Telegram accounts recover over SMS, so this inherits SIM-level risk. The pre-existing exposure was real but smaller: the bot already pushes task, mention, and deadline notifications, so a compromised Telegram account already leaks internal activity today — this raises it from read to read-write. **Accepted as-is (owner decision, v4) for a 10-30 person internal tool**: no 2FA, no time-of-day restrictions, no session-duration caps, no rate limiting beyond Supabase defaults. The only guard is the profile-state check in `equipment-auth` (§5). If this is ever revisited, the migration path is to move equipment writes behind a `gear-api` edge function, re-implementing authorization in Deno (§3's rejected alternative, kept on record for exactly this). Mechanically nothing else changes: the minted session is the user's ordinary session, every policy above applies to it exactly as to a browser login, and the HMAC check rests on bot-token secrecy — the same secret the webhook already depends on.
- Cron/edge auth unchanged (`CRON_SECRET`, service-role, webhook secret).

## 11. Decisions — all product decisions resolved
